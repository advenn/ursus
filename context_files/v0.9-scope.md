# ursus v0.9 — scope

**Theme: Parquet complete, then Apache Iceberg.**

The maintainer set it on 2026-11-14 (step 506), after the service theme of 0.8. They
confirmed the order on 2026-11-27, once v0.8.1 shipped: v0.9 first, then v0.10's
SQL. Polars is the list of what users need, not a specification (step 506 §1).
ursus's own answers stand where it answers differently for a reason, and are
documented. A release only adds (step 494).

The two halves are one theme, because Iceberg is Parquet files and metadata that
point at them:
- An Iceberg table's data files hold nested columns and maps, and name every
  column by a field ID.
- Its pruning reads the column statistics and partition values Parquet carries.

So Parquet's half comes first, and each of its items is something Iceberg's half
needs or something a Parquet user already asks for.

**Where it stands** (surveyed at step 548 by reading master's code, `1d2dc1b`; no
measurement was taken, the laptop kept quiet):

- **Read.** A flat column, a List of a primitive and a Struct of primitive fields
  are read. A list of lists, a list of structs, a struct holding either, and a map
  are refused by name when a query reads them (`internal/source/parquet/types.go`,
  `nested.go`). There are two paths:
  - ursus's own page reader (`checkedPages`, `colreader.go`) for what it decodes
    itself;
  - arrow-go's `pqarrow` for the rest, behind the footer walk and the guards of the
    0.8 bug hunt.
- **Write.** ursus's own writer (`writer.go`, `nestedNode`) writes what the reader
  reads, and refuses the rest by name, "a writer whose output its own reader rejects
  is worse than one that says so".
- **Types in memory** already nest at any depth: `List(List(String))`, a Struct of
  Lists, an Array. Only Parquet stops at one level.
- **There is no Map type.** A Parquet MAP has no ursus column to land in.
- **Field IDs** are neither read nor written: no file in the module names one.
- **Key-value metadata** is read inside the reader (the embedded `ARROW:schema`)
  and written by the writer, but no public API exposes it.
- **Page indexes and bloom filters** are neither read nor written.
- **Write options** are the codec for every column (`WithCompression`), the rows a
  row group holds, and statistics on or off. There is no compression level, no
  per-column codec, encoding or dictionary, and no metadata.
- **arrow-go v18.9.0, already a dependency,** has what several items lean on:
  - writer properties for page indexes, bloom filters, a codec and level per column,
    and an encoding and dictionary per column (`parquet/writer_properties.go`);
  - readers of a page index and of a bloom filter (`parquet/metadata/page_index.go`,
    `bloom_filter.go`);
  - field IDs in `pqarrow`'s schema mapping;
  - **an Avro object-container reader into Arrow (`arrow/avro`)**, which Iceberg's
    manifests may need instead of a new dependency (I1).
- **The guards stay in front.** Every new path reads only past the footer walk, the
  bounded allocator, `fuzzcheck`'s limits and the 0.8 hunt's guards (steps 508–546).
  A new decoder or reader gets a fuzz target before it ships.

## 1. Parquet

### P1. Nested columns at any depth, read and written

A list of lists, a list of structs, a struct holding lists or structs, at any depth
the footer walk allows (`maxSchemaDepth`), are read into ursus's own nested types and
written from them. The repetition and definition levels follow the standard
three-level LIST encoding that pyarrow, Polars and Spark write, and the two-level
legacy forms a reader meets in old files, as pyarrow reads them.

The read path is a choice for the step: decode nested levels in ursus's own page
reader, or take `pqarrow`'s arrays and convert them. Measure both on the step's
micro-benchmark before committing.

The writer writes what the reader reads, and nothing it cannot read back.

**Oracle:** pyarrow 25 and Polars 2.1. Their files are read, and recorded answers
held, under `testdata/oracle`. Each depth is round-tripped through ursus, and
through pyarrow on CI.

### P2. A map read as a list of key-value structs

A MAP column reads as `List(Struct(key, value))`, which is Polars' answer too, since
ursus has no Map type and adding one is not this theme. Keys keep their order, and a
null map is a null list.

On write, a `List(Struct(key, value))` is written as a list of structs by default.
An option writes it as a MAP annotation, which Iceberg's writers and readers expect
(decision 3).

### P3. Field IDs, read and written

A file's field IDs are read into the schema ursus reports (`ReadParquetSchema` and a
Field's metadata, as an addition), and written from the caller's choice: an option
naming each column's ID, and the IDs a read column carries passed through on write.

This is the item Iceberg depends on most. Columns are matched by ID, so a renamed or
reordered column reads (I2).

### P4. Page indexes and bloom filters, read to skip and written

- **Read.** A filter on a column with a page index skips the pages whose min and max
  rule it out, beyond today's row-group statistics. An equality or `IsIn` filter on a
  column with a bloom filter skips the row groups the filter rules out. Both are
  checked against the answer without them, as the pruning differential of step 71
  checks statistics.
- **Write.** Options write page indexes, and bloom filters for named columns at a
  false-positive rate.
- **Guards.** A page index and a bloom filter are untrusted input like a footer:
  bounded by the bytes the chunk holds, walked before arrow-go reads them, each with
  a fuzz target.

### P5. Write options and metadata

- a compression level, and a codec, a level, an encoding and a dictionary for each
  column, over arrow-go's writer properties;
- key-value metadata written (`WithParquetMetadata`) and read (`ParquetMetadata`, a
  file's map), both additions.

The defaults do not change: a file written by 0.8 and by 0.9 with no option is the
same file.

### P6. A footer cache

A service that scans the same files often re-reads and re-walks each footer. An
engine-level cache keyed by the file's identity (path, size and modification time,
or the opener's own key) keeps the parsed and walked footer within a byte budget,
evicting least-recently used. It is off unless asked (`WithFooterCache`, an
addition), and measured on the 0.8 service probe's small queries before it is
recommended.

## 2. Apache Iceberg

### I1. Reading Avro: arrow-go's, or ursus's own

Iceberg's manifest lists and manifests are Avro object-container files. The first
step is a spike: read the manifests of tables pyiceberg and Spark write through
arrow-go's `arrow/avro`, and check:
- its schema mapping: records, arrays, maps and the null unions Iceberg uses;
- its behaviour on crafted input, under fuzzcheck.

If it holds, Iceberg costs no new dependency. If it does not, ursus reads the subset
of Avro manifests use itself. That is a small, fixed schema, but it would be a
decoder of its own, with a fuzz target (decision 1).

### I2. Read a table

Read a table from its location:
1. the current metadata file;
2. the snapshot asked for: the current one, one by ID, or one as of a time;
3. its manifest list, its manifests, and their data files, read through P1–P3's
   Parquet.

Columns are matched by field ID, so the table's schema evolution reads:
- a column renamed, reordered, added (null in older files) or dropped;
- a type promoted as Iceberg allows: int to long, float to double, and a decimal's
  precision widened.

Format v1 and v2 tables are read. v3's deletion vectors are noted, not built.

### I3. Pruning

A filter skips data files by their partition values, under the identity, bucket,
truncate, year, month, day and hour transforms. It also skips files by the column
bounds and null counts in their manifest entries, before any data file is opened. A
differential against the answer without pruning holds it, as step 71's does for
Parquet.

### I4. Deletes

v2 position deletes and equality deletes are applied to the files they name. Each is
checked against the same table with the deleted rows removed by hand: a table
written twice, once with deletes and once without.

### I5. Write: append and overwrite

A frame is appended, or overwrites the table or a partition. The data files are
written by P1–P5's writer with field IDs, and the manifests and a new snapshot are
committed. A path catalog commits by writing the next metadata version and swapping
its pointer. A concurrent commit is detected and refused, never merged silently.

### I6. Catalogs and storage

A table's path comes first, as a filesystem or an `fs.FS` holds it. The REST catalog
comes next, over the caller's `http.Client` (decision 2). Storage goes through
ursus's openers and `fs.FS`, as for every format. Object stores stay the caller's,
as `feature-gaps.md` §7 has them.

## 3. Testing

As since 2026-11-05 (`tests-from-oracles`), expected data comes from:
- recorded answers: pyarrow 25 and Polars 2.1 for Parquet; pyiceberg and its tables,
  written by pyiceberg and by Spark where CI can, for Iceberg;
- a Go oracle;
- or a differential over generated inputs.

It never comes from hand-typed tables. qcheck's generator gains nested columns as P1
lands, and DuckDB's iceberg extension may serve as a second reader on CI.

**Measurements** are micro-benchmarks and single queries only. Full suites run
neither on the laptop nor on GitHub's runners (steps 540 and the maintainer's word);
v0.9's report states where its full-size figures come from, or that it has none.

## 4. Decisions, taken on 2026-11-27

The maintainer took each recommendation:

1. **Avro:** arrow-go's `arrow/avro`, if I1's spike holds on real manifests and
   under fuzzing; a reader of ursus's own for the manifests' subset only if it does
   not.
2. **The REST catalog:** in a v0.9.x, after the path catalog.
3. **Writing a map:** a `List(Struct(key, value))` is written as a list of structs
   by default, and as a MAP when an option asks.
4. **v0.9.0** is tagged after Iceberg read (I1–I4). Writing and catalogs (I5–I6)
   come in v0.9.x releases.

## 5. Considered and left

- **A Map type in ursus:** a type of its own throughout the engine, not this theme;
  P2's list of structs is Polars' answer too.
- **Delta Lake, Avro write in general, and Iceberg v3's deletion vectors:** later,
  each on request.
- **Object stores by URI:** still the caller's, through openers (§7).
- **Parquet encryption and the variant and geospatial logical types:** refused by
  name, as today.
- **ursus's own zstd decoder:** v0.11's structural performance, as step 506's plan
  has it.

## 6. Order

1. **P5 and P3** first, small, and needed by everything after.
2. **P1** (nesting) and **P2** (maps), with their oracles.
3. **P4** (page indexes, bloom filters) with fuzz targets, then **P6** (the footer
   cache), measured.
4. **I1**'s spike decides Avro. Then **I2**, **I3** and **I4**, reading.
5. **I5** and **I6**, writing and catalogs.

Each step is a branch and a pull request with green CI, as every change since
2026-10-30. Each bug found on the way is fixed in its own step, or recorded in
`feature-gaps.md` if its theme is another's.
