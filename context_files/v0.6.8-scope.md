# ursus v0.6.8 — scope

**Theme: the leftovers of feature completeness, and five of 0.7's performance tasks
done ahead of it.**

The maintainer set it on 2026-10-26, tagging v0.6.7: "don't jump to 0.7 yet, continue
on 0.6.x; 0.6.8 for the leftovers: partitioned writes, large strings, write_database;
take several tasks from your table for 0.7, and do them till 0.7." 0.6.7 had already
built what was to be 0.6.8's I/O and the types after it.

Each item below was surveyed in the code at step 365; the file and line references are
that survey's.

**Where it stands:**

- written at step 365;
- step 366 built L1, a database written: `WriteDatabase`, its modes and four
  dialects, checked against a recording driver and round-tripped through a real
  SQLite outside the repository;
- step 367 built L2, partitioned writes, for the four sinks: Polars' tree name for
  name, each reading the other's dataset as the frame. An empty hive key of text now
  reads as the empty string, as Polars reads it;
- step 368 built L3, large strings: 64-bit offsets made by the combiners past 2 GiB,
  read through the accessor, exported as a LargeString, read back, split for IPC and
  spilled; a real 3 GiB column checked in CI's `bigstrings` job;
- step 369 built P1, `Profile`: each node's span, rows, batches, own time and peak
  memory, wrapping only where asked; `ExplainOptFlags`;
- step 370 built P2, a count reads no column: a scan of no columns, which each
  source answers with its rows or with its cheapest column; `Count` over lineitem in
  2.5 ms where it took 400–500.

## 1. The leftovers

### L1. A database written

Polars' `DataFrame.write_database(table_name, connection, if_table_exists="fail")`
writes a frame to a table and answers the rows it wrote. ursus reads a database since
step 353 (`database.go`, `internal/source/sqlrows`), through `database/sql`, and
writes none.

- **`LazyFrame.WriteDatabase(ctx, db, table, opts...) (int64, error)`,** and the
  `DataFrame` method, over anything with `ExecContext` and `BeginTx`: a `*sql.DB` or a
  `*sql.Conn`. The rows go in batches, in one transaction.
- **`WithIfTableExists(Fail | Replace | Append)`,** Polars' modes. Fail checks the
  table first and refuses; Replace drops and creates it; Append inserts into what is
  there, and creates a table that is missing, as Polars' does.
- **The dialect:** `database/sql` cannot name it, so `WithDialect(...)` names it, and
  without it the driver's type names it: SQLite, PostgreSQL, MySQL and SQL Server.
  The dialect gives:
  - the placeholders, `?`, `$n` or `@pn`;
  - the quoting of names;
  - the columns' types in `CREATE TABLE`: an Int64 a `BIGINT`, a String `TEXT`, an
    instant with a zone `TIMESTAMPTZ` or its kin;
  - the most parameters a statement takes, which sizes each batch.
- **Values:** each column as `ReadDatabase` reads it back, so a write and a read are a
  round trip, a Decimal as its text, a List or a Struct refused by name.
- **Tests:** step 353's fake driver learns `Exec` and records each statement and its
  arguments. A round trip through a real SQLite runs outside the repository, as step
  353's did, so `go.mod` gains no driver.

### L2. Partitioned writes

Polars writes a hive dataset: `write_parquet(dir, partition_by=[...])`, and
`sink_parquet(pl.PartitionBy(dir, key=..., include_key=..., max_rows_per_file=...))`,
and likewise for CSV, IPC and NDJSON. Polars 1.44.1, probed at step 365:

- a file `k=a/t=2024-01-02/00000000.parquet` a key, numbered from zero, a new one when
  `max_rows_per_file` is reached;
- a key's text percent-escaped: `/`, `=`, a space, `%`, `:` and anything past ASCII,
  `a/b` as `a%2Fb`, `ü` as `%C3%BC`;
- a null key as `__HIVE_DEFAULT_PARTITION__`, an empty one as `k=`;
- the key columns kept in each file, or dropped with `include_key=False`.

ursus reads such a dataset since step 347 (`internal/source/hive`), and writes none.

- **`WithPartitionBy(keys...)`** for `SinkParquet`, `SinkCSV`, `SinkIPC` and
  `SinkNDJSON`, with `WithPartitionIncludeKey(bool)` and `WithMaxRowsPerFile(n)`.
- **Streamed:** each batch's rows are routed by their key to the key's open writer,
  numbered as Polars numbers them. A key's file is written to a temporary name and
  renamed when it closes, as each sink's file is today; the four copies of that
  (`parquet.go:377`, `csv.go:434`, `ipc.go:321`, `jsonwrite.go:53`) become one helper.
- **Open files are bounded:** past a limit of open writers, the least recent closes
  and a later row of its key opens the next number, so a dataset of many keys writes
  without one file handle a key.
- **The values' text** is the one the hive reader parses back, an instant's and a
  date's as Polars writes them, and `hive.Format` sits beside `hive.ParseFor`.
- **A round trip:** written by ursus and read by Polars, and written by Polars and
  read by ursus, the same frame. Where Polars reads an empty key as the empty string
  and ursus as null, one of them is recorded in §9 or changed.

### L3. Large strings

A String or Binary column holds at most 2 GiB of characters: its offsets are 32-bit,
and past them it refuses (`data.MaxStringBytes`, `column.go:254`). One contiguous
column is what a collected frame holds (`frame.go:21`, `exec.go:44`), and what every
operator that concatenates builds: the join's build side, a window, the sort's keys, an
aggregation's.

- **64-bit offsets as a second representation** of a String or Binary column,
  `offs64`, as `context_files/design/physical.md`'s `LayoutOffset64` planned. Lists
  keep theirs.
- **Made only by the combiners:** `ConcatStrings`, `TakeStrings` and its chunked form
  switch to 64-bit offsets when the total passes 2 GiB. The sources build a batch at
  a time and keep 32-bit ones.
- **Read through `StringAccessor`,** which already hides them from about 68 call sites
  in 46 files; `Get` and `Bytes` take one branch on the layout. The few that read
  offsets themselves learn the second form: `Slice`, `nbytes.go`, the Arrow export,
  which writes a `LARGE_STRING`, and the spill format, which gains a kind.
- **`RawOffsets`** gains a 64-bit companion, and an exported doc says which a column
  holds.
- **Tests:** `MaxStringBytes` is a variable, so a test lowers it and every path above
  meets a column past it, at the sizes of a unit test; one test, outside the gate,
  builds a real 3 GiB column.

## 2. Five of 0.7's performance tasks

Each is in `feature-gaps.md` §8. Each is measured before and after, against Polars where
Polars runs it, and with an A/B against v0.6.7's runner on the suites it touches.

### P1. `Profile`

Polars' `LazyFrame.profile()` answers the frame and a frame of each node's start and
end, in microseconds. ursus explains a plan (`lazy.go:244`, `internal/plan/explain.go`)
and times nothing: an `Operator` is `Schema`, `Next` and `Close` (`operator.go:50`).

- **`LazyFrame.Profile(ctx, opts...) (*DataFrame, *DataFrame, error)`:** the answer,
  and a frame of each operator: its node, its rows and batches out, its time inclusive
  and its own, and the memory its account held at its peak.
- **Wrapped where the plan is lowered,** `physical.Plan` (`operator.go:478`). A stage's
  `BatchOp` is wrapped inside it, with atomic counters, since a stage the parallel pool
  runs is found by its type (`parallel.go:294`): wrapping the stage itself would turn
  the parallelism off. A breaker's time is its consuming and its finishing.
- **Off, it costs nothing:** no wrapper is built unless `Profile` asks.
- `Explain` honours `OptFlags`, which it ignores (`lazy.go:287`).

### P2. A count reads no column

`Select(Len())` over a Parquet scan reads every column, where Polars reads none. The
projection pushdown asks for no column, and a nil projection means every column
(`rule_projection.go:486`, `nodes.go:42`).

- **An empty projection is a scan of no columns,** `[]string{}` where it was nil, and
  every source answers it with batches of rows and no columns: Parquet from its
  footers' row counts, reading no column chunk; CSV, NDJSON and IPC as their rows are
  counted; memory at once.
- `trimOp` builds its batches with their row count (`NewBatchRows`), not from the
  columns, so a batch of no columns keeps its rows; the union's and the hstack's
  narrowest-column workaround (`rule_projection.go:868`, `:959`) goes.
- **Measured:** `Select(Len())` and `Count` over the PDS-H lineitem file, against
  Polars'.

### P3. Slice pushdown

A limit reaches a scan or a sort only when it sits directly above it
(`rule_limit.go:48`).

- **Through the nodes that keep rows,** a projection, `WithColumns`, a row index: to a
  scan's `MaxRows`, or a sort's top-k.
- **A slice with an offset** is a limit of its offset and length beneath it.
- **Into each input of a union,** the union keeping its own; **into a left join's left
  input**, where the join keeps its left order, the join keeping its own.
- A filter, a group-by and every other join stay barriers.
- **The plans change,** so each changed plan of the 34 golden ones and the 37 the
  suites run is listed and checked by hand, and the answers are the same.

### P4. A frame's aggregate without a group-by's machinery

An aggregate over the whole frame is a group-by of no keys (`agg.go:150`, `:232`): each
batch appends a zero group id a row, and an integer `Mean` copies its column to Int128
first (`kernel/agg.go:875`, `window.go:586`). A mean of a million Int64s takes 4.8 ms
where Polars takes 0.47; `Min` 1.6 and `First` 2.6.

- **A keyless fast path:** an accumulator that can, takes a whole column at once
  (`AddAll`), summing in locals, an Int64's mean in 128 bits by carries, counting by
  the null count; no group ids are made.
- **The same answers to the bit,** a float's sum in the same order as now, so a
  frame's `Sum` and `Mean` do not change their last bits.

### P5. A CSV file read faster

A million rows of an integer, two text columns and a float, 42 MB, take 76 ms where
Polars takes 22. Each block's records are scanned one at a time and appended a field at
a time, a builder's interface call each, and a float is scanned twice: once to check
its syntax and again by `strconv.ParseFloat` (`parallel.go:143`, `csv.go:723`,
`numtext.go:21`).

- **A column at a time:** a block's fields located once, as the serial path's
  `colStage` locates them (`csv.go:777`), then each column parsed in one loop, its
  validity set in bulk.
- **A float parsed in one pass,** over the bytes, to Go's answer exactly: the fast
  path for the common decimal, `strconv` for the rest, checked against `strconv` over
  every float shape the reader's tests and Polars' accept.
- **Measured** on step 357's file, and the CSV suites' queries against v0.6.7's
  runner.

## 3. The claims

- **The leftovers answer as Polars 1.44.1 does,** checked on the same inputs, or a
  difference is recorded in `feature-gaps.md` §9.
- **The performance items change no answer,** to the bit where the answer is a float.
- **No regression:** the plans change only where P2 and P3 change them, each change
  listed; the suites' queries are timed against v0.6.7's runner, alternating, where a
  step touches their path.
- **Each step:** tests and teeth that bite; the light gate, one package at a time, CI's
  every width, scalar build and race detector after the push; the 22 PDS-H answers.
