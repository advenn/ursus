# v0.3 — scope

**Authoritative over [`dataframe-features.md`](./dataframe-features.md) §14's v0.3
line**, which was written before any of ursus existed and has not been revisited
since. That line is kept where it is as a record of what was expected; this document
is what the milestone actually is.

Everything below was measured against the tree at step 64, not read off a checklist.
Where a claim comes from running code rather than from a comment, it says so.

---

## 1. The original list, measured

> **v0.3:** list/struct namespaces, `Pivot`/`Unpivot`, SQL frontend, cloud object
> stores, Delta/Iceberg, plan serialization, SIMD kernel coverage across all
> primitive types.
>
> — `dataframe-features.md:688`

| item | status |
| --- | --- |
| list/struct namespaces | **done** — 14 `.list` functions and `.struct.field()` |
| `Unpivot` | **done** |
| `Pivot` | not started, and blocked on a real design problem: its output columns are the distinct values of a column, so its schema depends on DATA, and no plan node here has a data-dependent schema |
| SQL frontend | not started |
| cloud object stores | **not started** — `objstore/` is specified at `ursus-api.md:67` and `:1079` with `S3`/`GCS`/`HTTP` constructors; there is no such package and no code mentions a URI scheme |
| Delta/Iceberg | not started |
| plan serialization | not started — nothing in `internal/plan` marshals |
| SIMD across all primitive types | **Float64 only**, and within Float64 only six compare-against-constant kernels plus `addF64SIMD` and `mulF64SIMD` (`internal/kernel/simd_amd64.go`). No integer SIMD exists |

**Two of eight.**

The list is also weighted oddly for a v0 milestone. Delta/Iceberg and plan
serialization are strategic bets rather than things a user is blocked on; SQL is an
entire frontend. None of the three is why anybody would or would not use this
library today.

## 2. What the list missed

Four gaps that no scope document mentions and that a user meets in the first hour.
All four were measured against the tree at step 64 — §2.1 and §2.2 by running the
public API, §2.3 by building the column, §2.4 from the budget's own enumeration.

### 2.1 Decimal is a dead-end type

The README advertises **Decimal (128-bit)** in its types table. Measured, through
`ResolveBinary`, `ResolveAggBinding` and `CanCast`:

| operation | Decimal |
| --- | --- |
| `+` `-`, comparison, `min` | **works** — measured |
| `max` `first` `last` `count` `n_unique` | work, per `decimalAggUnsupported`'s doc: they "select or count rather than compute, so the unscaled integer they carry around is still the right number with the right scale" |
| `*` `/` | refused — *"operator * is not defined for Decimal(18, 3)"* |
| `sum()` `mean()` | refused — `internal/expr/agg.go:368` |
| cast to or from **any** numeric type | `CanCast` is **false** in both directions |
| cast to String | works — the only way out of the type |

So a money column can be read, added, compared and written, and cannot be
**summed**. Summing money is the use case.

The refusal itself is deliberate and well argued — `decimalAggUnsupported`'s doc says
the precision calculus is undecided, *"sum's result needs a wider precision than its
input, and guessing which is a decision better made deliberately than by whichever
branch happened to be reached first"* — and refusing at plan time is the right
holding position.

**Its hint is not.** The error says:

> cast to Float64 first if approximate arithmetic is acceptable

and `CanCast(Decimal(18,3), Float64)` is `false`. The advice cannot be followed. This
is the same shape as the as-of join telling a caller to filter nulls out of a
not-null column (step 63 §5) — a refusal whose remedy does not exist.

**Fixed, and it was not the one line this document first called it.** The same
sentence appeared in **five** refusals across three files — the seven computing
aggregates, `*` and `/`, `floor`/`ceil`/`sign`, the `sqrt` family, and `round` — so
the advice now lives in one `decimalRemedy` helper and names what a caller can
actually do: which operations are exact on a Decimal, and that the unscaled integers
can be read with `df.Column[ursus.Int128Value](name)` and scaled by hand. The guard
against it coming back generalises past this bug: a sweep scans every Decimal
refusal for cast recommendations and asserts `CanCast` permits each one, with an
Int128 refusal as the control that proves the scanner is not simply finding nothing.
The refusals themselves are unchanged — `sum(Decimal)` still refuses, and should,
until §3 item 2 is decided.

### 2.2 Nested data has no round trip

Measured:

```
ScanParquet(list file).SinkParquet(...)
  ursus: sink_parquet: cannot write column "tags" of type List(Int64) to Parquet
ScanParquet(list file).SinkCSV(...)
  ursus: sink_csv: cannot write column "tags" of type List(Int64) to CSV
```

Arrow export of the same frame succeeds. So ursus reads List and Struct from Parquet
and Arrow, gives them a namespace each, and cannot write them back to the format they
came from. Refused cleanly rather than corrupting anything, which is the right
failure — but reading a file you cannot write is a poor first impression, and it is
the obvious completion of work already done.

### 2.3 Enum is read-only, and hides a latent panic

`dtype.Enum(cats...)` builds the TYPE, and nothing in the public API builds a COLUMN
of it: `Values[T Literal]` has no enum case and `CanCast` refuses every cast into an
Enum. An Enum column can only arrive from a Parquet or Arrow dictionary.

It also carries a panic that is unreachable *only* because of that. `IsString()` is
true for an Enum, so `CanCast` admits `Enum -> numeric`, and `parseFromString` opens
with `c.Strings()` on a column whose payload is uint32 indices:

```
panic: runtime error: index out of range [0] with length 0
```

Measured at step 64, by putting an Enum column into the evaluator contract fixture;
it is why `noContractColumn` excuses Enum with the panic written down. `ResolveCall`
names the same hazard independently and calls it *"latent today only because Enum
columns cannot yet be built from the public API"*. **Making Enum constructible
without fixing the cast surface turns a latent panic into a reachable one**, so the
two are one piece of work, not two.

### 2.4 "Spills to disk rather than falling over" is half true

The README's opening sentence claims streaming execution that spills. Three operators
do. The budget's own hint enumerates the rest (`internal/execopt/budget.go:279`):

> sort, group_by and join spill to disk; the other buffering operators — over,
> reverse, hstack, tail and unique — fail rather than exceed the limit

and that enumeration is itself incomplete: `join_asof`, `rolling` and `merge_sorted`
also fail and are named in neither the hint nor `WithMemoryLimit`'s doc
(`lazy.go:319`). `over` and `unique` are common enough that the claim oversells.

Separately, the as-of build sink's ceiling is enforced against roughly **half** its
true peak: `Probe` materialises a second full copy of the right side through
`kernel.Concat` plus a bucket map, and accounts neither, with no `Check` after the
last `Consume`.

## 3. The scope

**v0.3 is "the types and the I/O are honest".** Five items, in dependency order.

1. ~~**Fix the impossible hint.**~~ **Done.** It was five refusals rather than one,
   and it needed no design decision — see §2.1. The instrument that keeps it fixed is
   worth more than the fix: it checks that a refusal only ever recommends a cast the
   library permits, which is a rule with no Decimal in it.
2. **Decide decimal aggregation.** Commit to a precision-and-scale rule for `sum` and
   `mean`, implement it, and add `Decimal <-> numeric` casts. This is the item that
   turns Decimal from advertised into usable. It is an API commitment, so it wants
   the same treatment `mean(Duration)`'s rounding got in step 62: the rule written
   down with its justification, and a tooth that fails if it silently changes.
3. **Nested write to Parquet.** Closes the round trip.
4. **Cloud object stores.** The one item from the original list that unlocks users
   rather than checking a box — most Parquet lives in S3. `ursus-api.md` §9 already
   specifies the shape.
5. **The two open silent wrong answers**, both surveyed at step 64 and neither fixed:
   - ~~**UDF name uniqueness.**~~ **Done — step 65.** `plan.CheckUDFNames` refuses
     two udfs sharing a name, at the top of `Resolve`, which is where it has to be:
     `extractWindows` deletes the losing subtree on a merge, so a check placed after
     the walk passes on the very query it exists to refuse. It was **four** maps, not
     three — `internal/physical/tempgroup.go` appeared in no list.

     **The remedy this entry recommended does not work, and that is the lesson.**
     `reflect.ValueOf(impl).Pointer()` returns the *code* pointer, and every
     `MapElements` udf in a program closes over one func literal, so it answers
     "same" for every pair and a check built on it detects nothing. An unexported
     minted id does the job. The original text is kept below, wrong remedy included,
     because a scope document that quietly edits its own mistakes is worth less than
     one that shows them.

     `checkUDF` refuses an empty name and nothing refuses a
     duplicate; `UDF.String()` renders the name and declared type and never the
     closure; three dedup maps key on that rendering. Two different functions under
     one name over the same column collapse into one computation and **both results
     come from whichever was seen first**, with no error. `udf.go`'s own doc states
     the consequence and does not enforce it. The trap: `kernel.ColumnUDF` is a named
     func type, so `==` on two `UDFImpl` values **panics** — identity must go through
     `reflect.ValueOf(impl).Pointer()`.
   - ~~**`dtype.Interval.Every` accumulates unchecked.**~~ **Done — step 66.** Both
     halves of each accumulation are checked, bounded by each type's MAXIMUM so the
     negation is total by construction. It was never only the parser: `IntervalOf`
     and `FromDuration` took unvalidated input too, and two of those defects needed
     no overflow at all. Original text follows.

     `Every("357913942y")` is
     silently **8 months**, `Every("613566757w")` is **3 days**, each with
     `Err() == nil` and `Negative() == false`, passing every downstream gate. It
     reaches `GroupByDynamic`/`Rolling`, the as-of tolerance and `dt.Truncate`.

And one either/or, which is a decision rather than work:

6. **Either make `unique` and `over` spill, or soften the README.** Both are
   defensible; what is not defensible is the current gap between the sentence and the
   behaviour. Softening is a paragraph. Spilling `unique` is comparable to the hash
   aggregation's radix routing and reuses it; spilling `over` is harder, and
   `windowSink.Merge` already says why it cannot be split — *"needs a group-id
   remap it does not have: two sinks assigned different partition numbering, so
   folding them would attribute one partition's window value to another"*.
   Anything that spills a window has to solve that numbering first.

## 4. Deliberately deferred, with the reason

- **SQL frontend** — an entire parser, binder and type checker. It is the largest
  single item ever proposed for this project and it does not make any existing
  feature work better. It wants its own milestone.
- **Delta/Iceberg** — table formats are a commitment to a catalogue, a transaction
  log and someone else's spec version. Premature while object storage does not exist.
- **Plan serialization** — no consumer asks for it yet. `Explain`'s output is already
  snapshot-tested by the golden inventory, which is what the requirement was actually
  for.
- **`Pivot`** — blocked on the data-dependent-schema problem above, which is a plan
  architecture question and not a feature.
- **SIMD beyond Float64** — a performance item, and the profile says it is not where
  the time goes. Step 18 and step 20 both found the wins elsewhere (order keys,
  per-value allocation, `extremumAcc`). Widening SIMD before re-profiling would be
  optimising by checklist.
- **The expression long tail** — `Expr.Rolling*`, `Upsample`, `Interpolate`, the
  trigonometric and bit-count blocks, `MapGroups`, CSE. All additive, none blocking.
  The 25 `Rolling*` methods additionally need a frame concept `WinParams` does not
  have, so they are not the small job the count suggests.

## 5. What the release claim becomes

v0.2's README says *"nothing here is promised"* and that stays true — Go's v0 rule
does not change at 0.3. What changes is that three sentences in it stop being
approximations:

- the types table stops advertising a Decimal that cannot be summed and an Enum that
  cannot be built;
- "Parquet and CSV (read and write)" stops meaning "read more than it writes";
- "spills to disk rather than falling over" either becomes true of the operators
  users actually hit, or says which ones it is true of.

That is a smaller claim than the original list and a much more defensible one.

## 6. Sizing, honestly

Items 1 and 5 are step-sized and resemble the last ten steps. Items 2, 3 and 4 are
not, and saying so is the point of this section.

- **Decimal aggregation** is an API commitment that will be hard to change later.
  Expect the decision to take longer than the code.
- **Nested Parquet write** means def/rep level ENCODING, which the reader's fixtures
  only ever decode — `writeElemLists` exists in the tests precisely because *"ursus
  cannot write nested Parquet, so the fixture has to come from the layer below"*.
- **Object storage** is a new package plus credentials, retries, ranged reads and a
  failure taxonomy, and it sits under the Parquet reader's existing assumption of a
  seekable local file. It is the largest item here and the one most likely to be its
  own milestone once started.

Nothing above is committed. This document records what the milestone should be and
what each part costs; the order in §3 is a recommendation, and items 1 and 5 are the
only ones that should happen regardless of how the rest is scheduled.
