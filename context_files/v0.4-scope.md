# v0.4 — scope

**This document scopes 0.4.** It is drawn from three things:

- the v0.3.0 benchmark report (`bench/results/REPORT.md`, produced from `ea43952`);
- every defect still recorded open in `audit.md` and the as-builts' "Still open"
  sections;
- every feature the design documents promised and the tree does not have:
  `ursus-api.md`, `dataframe-features.md` and `foundation.md`.

It was written against master at step 92. Where a claim names a file and line, it
was read there. Where it names a number, the number is in the report.

---

## 1. Where 0.3 leaves ursus

0.3 made the types and the I/O honest:

- **Decimal you can sum and multiply.**
- **An Enum you can build.**
- **Nested data round-trips through Parquet.**
- **A spill claim that is true.**
- **A source seam for object stores.**

The first full report after it found three things:

1. **ursus trails Polars** by about 3× on h2o and about 9–10× on PDS-H at SF=1.
2. **OOM exposure under containers.** ursus had no default budget, so a cgroup
   killed what a budget would have spilled. Steps 90 and 91 fixed this, released
   as v0.3.1.
3. **A group order that depended on scheduling** under an explicit limit. Step 92
   fixed it; it is not yet tagged.

## 2. What the surveys found

### 2.1 Why it is slow, from the code

**No profile has ever measured where a PDS-H query or an h2o join spends its
time.** Step 18 was scoped by a profiler, but only for the sort. Steps 38–39 asked
for an allocation profile, and none was taken. The causes below come from reading
the code and are ranked by how many queries each one plausibly moves. A profile
should re-rank them before any is built.

1. **The Parquet scan decodes on one goroutine.**
   - `reader.Next` takes `r.mu` for the whole decode
     (`internal/source/parquet/parquet.go:692`).
   - Nothing in the reader reads `ScanSpec.Threads`.
   - The bench files have 49–82 row groups of 122,880 rows each: plenty to split.
   - Every Parquet query pays this.
2. **The right side always builds a join.**
   - `internal/physical/join.go:1501` says so: *"The RIGHT side always builds. Not
     cost-based."*
   - In the PDS-H ports for q7, q8, q9 and q2, the right side is a fact table.
   - Step 36 also left the build serial.
3. **No common-subexpression elimination, and no reuse of a subplan.**
   - `internal/expr/cond.go:24` says so.
   - q15 and q2 build one frame and use it twice, so they compute it twice. That
     is q15's 30× and q2's 20×.
4. **Filters copy:**
   - A filter re-copies every column. There are no selection vectors.
   - A comparison with a literal first expands the literal to n elements.
   - The comparison bitmap is built bit by bit.
   - A cast temporal literal is not folded.

   q6, q1, q12, q14 and q19 are scan-and-filter queries.
5. **Top-n within a group (gb8)** is a rank window over a full sort, which is 92%
   of its time (step 24).
6. **Median (gb6)** keeps every value and sorts each group in full
   (`internal/kernel/aggstat.go`, `quantileAcc`). A selection would do.
7. **The parallel group-by** builds a full table per worker and merges them
   serially. `micro.txt` shows group-by plateauing at 2 threads.
8. **Peak memory is about 2× Polars.**
   - q21 allocates 12.68 GB for a 1.08 GB live set.
   - The build side keeps a second copy.
   - The final collect copies again.

### 2.2 What is still open, from the records

#### Reachable by a long-running service

- **`callCache` never evicts.** It is a process-global `sync.Map`
  (`internal/physical/eval.go:350`) memoising a compiled regex per Call node. It
  grows for the life of the process.
- **A failed plan does not close the operators it already opened.** For example,
  `planJoin` does not close its left side when the right fails, and there are
  about 17 such sites.
- **Rolling and GroupByDynamic expansion is not charged to the budget**
  (`internal/physical/tempgroup.go`). It is OOM-killed rather than refused, the
  exposure 0.3.1 removed everywhere else.
- **Go heap slack.** The default budget is half the ceiling because nothing sets
  GOMEMLIMIT.
  - gb10 over CSV peaks at 7.58 GB under an 8 GB cgroup, a thin margin.
  - The default budget is Linux-only.
- **I24:** the check that a non-nullable column holds no nulls runs in tests only.
- **List offsets are 32-bit with no guard.** S24 added the guard for String;
  List never got it.

#### A usability bug no changelog mentions

**Int128 supports only `+`, `-` and comparisons.** `*`, `//` and `%` are refused
with *"operator * is not implemented for Int128"*
(`internal/kernel/dispatch.go:841`). Every integer `Sum`, every Bool `Sum` and
UInt64 `Diff` return Int128, so `Col("x").Sum().Mul(2)` fails.

#### False refusals and misleading errors

- **J7:** as-of and `MergeSorted` key types.
- **J9:** a full join with coalesced keys.
- **J10, J11.**
- **J12:** `Concat` of a Null column.
- **I16:** unannotated fixed-length byte arrays.
- **I18:** writing a Null column.
- **I25, I26.**
- **S14:** UInt64 against an int literal.
- **S15–S17, S23.**
- **A8:** `Diff`, `PctChange` and `FillNull(Mean)` inside `.Over()`.
- **A9, A11–A13, A15.**
- **`!next.After`.**
- **`spill.Writer.Write`'s bare error.**

#### Unsupported, with a user waiting

- **Parquet:** INT96 timestamps, which Spark writes; the UUID and JSON logical
  types; BYTE_ARRAY Decimal.
- **Decimal:** `//`, `%` and `**`.
- **Datetime:** `mean`.

### 2.3 What was promised and not built

`ursus-api.md` specifies all of the following. None exists:

- **Stores and formats:**
  - an `objstore` package with S3, GCS and HTTP;
  - URI schemes and `List`-based globbing;
  - hive-partitioned reads and writes;
  - Arrow IPC and NDJSON;
  - a public `Source` interface. `Scan` takes an internal `plan.Source`.
- **Expressions:**
  - `Rolling*` expressions;
  - `strptime` and `strftime` with a format;
  - calendar-month offsets;
  - the selectors package;
  - `Describe`, `Sample`, `Cut`/`QCut`, `ValueCounts`;
  - `ConcatStr`;
  - list set operations, `List().Eval`, `Struct().WithFields`;
  - `MinBy`/`MaxBy`, `Corr`/`Cov`.
- **Larger work:**
  - `Pivot`;
  - SQL;
  - Delta and Iceberg;
  - plan serialization;
  - `MapGroups`.

## 3. The scope

**Theme: fast where it is slow, and safe inside a service.**

Object stores were first drafted into tier 1 and then **taken out of 0.4 by
decision.** §4 has the reason.

### Tier 1 — the release is not 0.4 without these

#### Performance: the structural causes, measured first

1. **Profile before building** (small).
   - A CPU profile of PDS-H q6, q7, q15 and q19 at SF=1, and of h2o j3.
   - The allocation profile steps 38–39 asked for.
   - A zero-row query to bound the fixed cost per query.

   The tier 1 and tier 2 performance items are re-ranked by what these show. The
   result is recorded in that step's as-built.
2. **Parallel Parquet decode** (medium).
   - Row groups or column chunks are decoded on `ScanSpec.Threads` goroutines.
   - Batches are re-sequenced, so order is kept.
   - This moves every Parquet query.
3. **Join build-side choice** (small to medium), then **a parallel build**
   (medium).
   - **The choice:** build the smaller side, judged from the footer row counts
     already read at plan time.
   - **The semantic decision comes first:** ursus keeps probe-side row order, and
     a swap changes it. Either keep the order by re-sequencing on the probe
     ordinal, or document that an inner join's order is unspecified.
   - **The parallel build:** needs `Merge` with a remapping of key ids.

#### Safe inside a service

4. **Bound or scope `callCache`.**
5. **Close what a failed plan opened,** at every site that opens a child and can
   then fail.
6. **Charge the expansion of Rolling and GroupByDynamic to the budget,** so it is
   refused rather than killed.
7. **GOMEMLIMIT.** Choose between two options and record the choice:
   - an opt-in `SetProcessMemoryLimit` derived from the detected ceiling;
   - a documented recipe.
8. **I24 in production.** Measure the check's cost with a micro-benchmark only,
   then turn it on, or turn it on behind an option.
9. **The 32-bit guard on List offsets,** as S24 gave String.

#### The usability bug

10. **Int128 `*`, `//` and `%`,** checked or widened, so that
    `Col("x").Sum().Mul(2)` works.

#### Release hygiene

11. **Tag v0.3.2** with step 92.
12. **Correct the record:**
    - The v0.3.0 changelog's limitations still list q7, and a budget that was
      only explicit.
    - The bench labels gb4 "large-cardinality integer groups", but `id4` has 100
      groups.
    - Put the Go engines' 5 ms memory sampler (`bench/engines/go/engine/engine.go:269`)
      behind a flag, since it perturbs what it measures.
    - Retire the stale `micro-opbench.log`.
    - Produce one full report at the end of 0.4.

### Tier 2 — should

#### Performance, second wave (each moves named queries)

13. **CSE, a `Cache` node, and subplan reuse.**
    - Moves q15 (30×), q2 (20×), q21, and the rest of q7.
14. **Top-n within a group as an operator.**
    - Moves gb8 (5.3×).
15. **Median by selection.**
    - Moves gb6.
16. **Filters without copying:** selection vectors, word-wise comparison bitmaps,
    and folding of temporal literals.
    - Moves q6, q1, q12, q14 and q19.
17. **A radix-partitioned parallel group-by,** in place of N full tables merged
    serially.
    - Moves gb3, gb5, gb7, gb10, q13 and q18, and peak memory.
18. **Read each Parquet footer once.** Today a footer is parsed at plan time
    (`parquet.go:162-167`) and again when the file is opened to be read
    (`:563-574`).
    - This was the one local gain inside the object-store item.

#### What users reach for first

19. **Time:**
    - `strptime` and `strftime` with a format (`Str().ToDate` takes none);
    - calendar offsets, `date + 1mo`. An `Interval` cannot reach arithmetic
      today.
    - `MonthStart` and `MonthEnd`, `IsLeapYear`, `Round`;
    - time-zone conversion.
20. **Windows:**
    - `Expr.Rolling*`, which needs a frame concept in the window parameters;
    - EWM;
    - `Interpolate`;
    - A8's `Diff`, `PctChange` and `FillNull(Mean)` inside `.Over()`.
21. **Everyday expressions:**
    - `Describe`, `Sample`, `ValueCounts`, `Cut` and `QCut`;
    - `ConcatStr`, `Str().Join`, `List().Join`;
    - list set operations, `List().Eval`;
    - `StructOf` as an expression, `Struct().WithFields`;
    - `MinBy`, `MaxBy`, `Corr`, `Cov`;
    - the trigonometric and bit-count block.
22. **I/O formats:**
    - Arrow IPC read and write (arrow-go's `ipc` is already in the dependency);
    - NDJSON read and write, through `encoding/json`;
    - INT96 timestamps;
    - Parquet UUID and JSON read as Binary and String;
    - hive-partitioned reads and writes;
    - multi-file schema drift;
    - the public `Source` interface.
23. **The false refusals and misleading errors of §2.2,** batched into one step as
    step 77 batched its own.
24. **Spill for `JoinAsOf`, `MergeSorted`, `Rolling` and `GroupByDynamic`,** after
    item 6 charges them to the budget.

## 4. Deliberately deferred, with the reason

| item | why not in 0.4 |
| --- | --- |
| Object stores (HTTP, S3, GCS; URIs, globbing, retries, a multipart sink) | **Skipped for 0.4 by decision.** 0.4 goes to speed and to service safety. Step 83's `ScanParquetFrom` and `ScanCSVFrom` still read through any store a caller can wrap in an `io.ReaderAt` or a stream. The design that was drafted is in this file's history: a standard-library HTTP range store, and S3 through a hand-written SigV4 signer. |
| SQL | A parser, a binder and a type checker: a milestone of its own. It should wait until the expression API it lowers to stops growing, and tier 2 is still growing it. |
| Delta and Iceberg | They need object stores first, which are themselves deferred, and they commit ursus to a catalogue and a transaction log. |
| `Pivot` | Its output schema depends on the data, and no plan node has a data-dependent schema. A static `Pivot`, given its output values explicitly, is possible. Decide when a step is planned for it. |
| Plan serialization | No consumer asks for it. Functions would first need registration by name. |
| Categorical, Array, nesting past one level | Enum covers the categorical use. Nesting deeper than List or Struct of a primitive waits for a user. |
| SIMD beyond Float64 | Item 1's profile decides. §2.1 suggests the time goes elsewhere. |
| I23, O13, the rest of J8, S26 | Each needs a measurement before a fix. J8 and S26 match what Polars does. |

## 5. What the release claim becomes

The 0.4 release claim can become:

> ursus runs inside a container or a long-lived service without being killed or
> leaking, and decodes, joins and filters on every core it is given.

The benchmark claim is whatever the end-of-0.4 report measures. **The target is
PDS-H SF=1 within 4× of Polars (geomean).** That is a target, not a promise:
item 1 decides whether it is reachable.

## 6. Order and sizing

1. **Items 4–12** — release hygiene and service safety. Each is small, and they
   protect existing users first.
2. **Item 1, then 2 and 3** — the profile, then parallel decode and build-side
   choice. Re-benchmark at SF=0.1 or with 2 million rows after each, never the
   full suite.
3. **Tier 2** — performance (items 13–18) in the order item 1 ranks it, then
   features 19–24.

Every step keeps the rhythm established by now:
- evidence first, with a two-way ratchet;
- the fix;
- teeth;
- the gate and PDS-H 22/22;
- an as-built.
