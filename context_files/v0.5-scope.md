# ursus v0.5 — scope

**Theme: close the gap to Polars, and build the features users reach for first.**
The maintainer chose both after v0.4.0 was tagged (step 139). Object stores stay out,
by decision, as they were for 0.4. SQL and the new I/O formats are later.

**Where it stands:**

- written at step 140, before any 0.5 work;
- step 141 took item 0's profile and re-ranked the speed items: 4, 1, 5, 2, 3;
- step 142 did item 4.

## 1. Where 0.4 leaves ursus

**Speed,** from step 127's report (commit `5a721e0`), ursus against Polars:

| suite | ursus | Polars | ratio |
| --- | --: | --: | --: |
| PDS-H SF=1, geomean | 310 ms | 70 ms | 4.43× |
| PDS-H SF=0.1, geomean | 35 ms | 9 ms | 4.01× |
| h2o 10M, Parquet | 914 ms | 475 ms | 1.93× |
| h2o 10M, CSV | 3,244 ms | 989 ms | 3.28× |

**The widest gaps, and what the records say causes them:**

| query | ratio | stated cause | evidence |
| --- | --: | --- | --- |
| q15, SF=1 | 10.5× | one `lineitem` group-by computed twice; no subplan reuse | read from the code (step 127; `pdsh.go`) |
| q2, SF=1 | 8.4× | a five-way join subtree used twice | read from the code (v0.4 scope §7 item 13) |
| q7, SF=1 | 7.0× | the reader, then the serial join build, then filters | profiled, but before steps 102–126 (step 101) |
| gb4, CSV | 7.0× | "mostly a scan" | timings only (step 117) |
| q19, SF=1 | 6.9× | `InSet` 16% of CPU; filters that copy | partly profiled (step 125) |
| q12, SF=1 | 6.3× | the serial join build, half its time | profiled (steps 125, 126) |
| q17, SF=1 | 5.5× | none recorded | — |
| gb1, CSV | 5.3× | "mostly a scan" | timings only |
| j3, Parquet | 3.7× | the reader, the probe's gather, `Collect`'s concatenation | profiled at 2M rows, before step 103's fix |

**What shapes the order:** none of the widest gaps was profiled after steps 123–126,
the round that changed the scan, the filter and the key table. Two of them have
causes read from the code, one has none, and two were inferred from timings alone.

**Memory:** after steps 128–138, h2o `gb10` and `j5` at ten million rows pass under a
3 GB container. Two allocation profiles (steps 132, 137) name what is left:

- the group-by's serial parallel fold: 24% of `gb10`'s allocation;
- the join's key table growing to ten million keys: 11 to 17% of `j5`'s;
- `Collect`'s contiguous result: a third or more of `j5`'s.

## 2. Tier 1 — must

### Speed

**0. Profile first.** S.

- **What:** CPU profiles of q15, q2, q7, q12, q17 and q19 at SF=1, and of `gb1` and
  `gb4` over CSV at ten million rows.
- **How:** one query at a time, with the runner's `-cpuprofile`. The laptop does not
  host full suites.
- **Then:** items 1 to 5 are re-ranked by what it finds, and §5's target confirmed or
  revised.

**1. CSE: a shared `Cache` plan node.** L. For q15 and q2; maybe q21.

- **Today:** a `LazyFrame` already shares node pointers. q15's per-supplier
  aggregate sits under both the supplier join and the global max. But `plan.Resolve`
  (`internal/plan/resolve.go`) is a `TransformUp`, which copies every shared
  subtree, so the optimizer sees a tree and the engine runs the subtree twice.
- **The change:**
  - A pass in `lazy.go` `compile` marks the shared subtrees that hold a join, an
    aggregate or a sort, and `Resolve` memoizes them by id.
  - Predicate pushdown treats a `Cache` as a barrier.
  - Projection pushdown gives the cached input the union of what every site reads
    (`rule_projection.go`).
  - The physical arm retains the result once, charged to the budget, spills past it,
    and every site replays it. Its close is counted, and Explain renders the shared
    subtree once.
- **Order:** q15 first, whose two copies read the same columns after pushdown; then
  q2, whose copies read different ones.
- **Risk:** a filter can no longer reach into a cached subtree, which is why only
  subtrees with a join, an aggregate or a sort are cached. Explain's golden outputs
  change.

**2. The group-by's parallel fold, partitioned.** M. This is stage (a) of the radix
group-by.

- **Today:** the fold in `parallelsink.go` is serial, through `hashAggSink.Merge`
  (`agg.go`), which re-inserts every key of every worker. That is 24% of `gb10`'s
  allocation (step 132).
- **The change:**
  - Phase one is unchanged.
  - Phase two merges P partitions on N goroutines, each into a fresh, presized sink,
    routing keys by the key table's stored hashes.
  - It uses hash bits other than the low four, which spill's `partitionOf` uses, so
    a partition does not land in a single spill bucket.
- **Risk:**
  - An unordered group-by's rows come out partition-major. The docs leave that order
    unspecified; the tests that compare exact order have to be found.
  - Peak memory holds every worker's table until every partition has merged.
  - The `goSerial` fallback still needs one sink.

**3. A partitioned, parallel join build.** L. For q12, whose build was half its time
(step 126), and q7, q4, q9, q21.

- **Today:** `parallelsink.go` declines joins, on purpose.
  - Round-robin dispatch breaks the premise of `joinBuildSink.Merge`: that the
    other sink read a later portion of the input. That premise is what keeps the
    match order.
  - `Merge` re-inserts every key serially anyway. A primary-key build side, such as
    q12's 1.5 million `orders` keys, would gain nothing.
- **The change:**
  - At `freeze`, split the retained rows by the key hash's high bits.
  - Build one `KeyTable` per partition in parallel, in global row order. A row's
    global id is its partition's base plus its local id. The CSR arrays and `rowKey`
    keep their shape.
  - The probe looks up by partition (`parjoin.go`). The key table gains a
    get-or-insert that takes a precomputed hash.
  - **Fallback:** today's streaming build, under a limit the caller set, past half
    the default budget, or once the build has spilled.
- **Risk:**
  - Rows within a key must stay ascending: a Left join's match order and the
    Right/Full flush depend on it.
  - A key must stay wholly resident or wholly routed through the fallback.
- **Shares** item 2's partitioning and hashed key-table API.

**4. Filters copy once; temporal literals fold.** S to M.

- **Filters today:** `filterOp` runs `kernel.FilterBatch` once per conjunct, and each
  run copies every column.
- **The change:** carry one selection across the conjuncts. Gather only the columns
  the next conjunct reads, and gather the rest once at the end.
- **Literals today:** the simplifier accepts a cast of a temporal literal, but
  `litFromColumn` (`fold.go`) refuses temporal types. So a date's cast runs on every
  batch, and the Parquet pruner never sees a date to prune on.
- **The change:** fold it to a literal of the column's type, with Explain rendering
  the date.
- **Risk:** a literal of another unit or time zone would prune wrongly and silently;
  it must match the column's type exactly.
- **The gain is probably small,** since PDS-H's dates are not clustered by row group.
  Item 0 says how small.

**5. A parallel CSV tokenizer, if item 0 confirms it.** M to L.

- **Today:** scanning runs on one goroutine. Conversion is split by column
  (`convertAll`, `csv.go`), so a two-column read gets two-way parallelism.
- **The evidence so far:** `gb1` and `gb4` trail 5.3× and 7.0× over CSV, against 3.4×
  and 3.7× over Parquet. Both read two or three columns.
- **Risk:** quoted fields that span chunk boundaries, and keeping row order.

### Features

**6. Windows.** M.

- **A8:** `Diff`, `PctChange` and `FillNull(Mean)` inside `.Over()` are refused
  today (`resolve_window.go`). Each is sugar over an inner window:
  - `Diff` is `w - Shift(w)`;
  - `FillNull(Mean)` is a `Coalesce` with `Mean().Over()`.

  `extractWindows` distributes an outer `Over` onto those inner windows. It must mark
  the sugar's own windows, so that a user's explicit `Over()` is not re-scoped.
- **Fixed-size `Rolling*`:** sum, mean, min, max, var and std.
  - They are new `WinFn` ops over the ordered segments `physical/window.go` already
    builds (`finishOrdered`).
  - Kernels: a running sum, a monotonic deque for min and max, and Welford with
    removal for var and std.
- **Care:** every new `WinParams` field must be in `args()`'s rendering, or two
  different windows share one temporary in the dedup maps.

**7. The calendar.** S each.

- **The functions:** `OffsetBy(Interval)`, `MonthStart`, `MonthEnd`, `IsLeapYear`,
  `dt.Round` and `ConvertTimeZone`.
- **Built on:** `dtype.Interval.AddTo` and `TruncateTo`, and `kernel/dtfn.go`'s
  `truncateCalendar`.
- **`ConvertTimeZone` only relabels:** ticks are UTC instants.
- **`date + 1mo` as arithmetic is not part of it:** an Interval is not an operand,
  and has no column type. `OffsetBy` is the call instead.

**8. Everyday expressions.** S each.

- **Composed from what exists:**
  - `ValueCounts`: a group-by, `Len` and a sort;
  - `Cut`: a `When` chain;
  - `QCut`: `Quantile().Over()` and `Cut`;
  - `Describe`: aggregates, concatenated;
  - `Str().Join`: `Implode`, then `List().Join`.
- **Small kernels:** `List().Join`, an N-argument `ConcatStr` (like `Coalesce`), the
  bit counts, and `StructOf` (`data.NewStruct` exists).

## 4. Tier 3 — later, each with its reason

| item | why not in 0.5 |
| --- | --- |
| selection vectors through every operator | XL: it changes every operator's input contract. Item 4 takes the local win. |
| the radix group-by's stage (b), partitioning in `Consume` | after stage (a) is measured |
| spill for Rolling, GroupByDynamic and as-of | it needs a family of sliding accumulators; they are bounded and charged since step 96 |
| a `DataFrame` of several batches | it would remove `Collect`'s concatenation, a third of `j5`'s allocation, but it changes what a `DataFrame` is |
| sizing the join's key table in advance | it needs a count of distinct keys, which ursus does not have; sized by rows, a build with few keys would hold empty slots the budget counts |
| a general `List().Eval` | the element-wise form comes first |
| object stores | out, by decision, as for 0.4 |
| SQL | a milestone of its own; the expression API is still growing in 0.5 |
| Arrow IPC, NDJSON, hive partitioning, schema drift, a public `Source` | outside 0.5's focus |
| Delta, Iceberg, `Pivot`, plan serialization, deeper nesting | as v0.4 scope §4 gives |

## 5. What 0.5 claims

> **ursus is within 3× of Polars on PDS-H at SF=1, and has the windows, calendar
> functions and everyday expressions a user reaches for first.**

**The target:** PDS-H SF=1 within 3× by geomean, from 4.43×, with q15 and q2 under
4×. Item 0 confirms or revises it before anything is built against it. The features
are done when they are built and tested, not by a number.
