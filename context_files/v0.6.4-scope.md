## 1. What still refuses under a budget

A refusal is a `KindResource` error naming the operator. Each row is a shape that
answers without a limit and refuses with one.

| shape | where | why |
| --- | --- | --- |
| a window over one huge partition with an order_by | `winstream.go:57`, `extwindow.go:61-71, 78-86` | `streamNeed` streams in the file's order only |
| rank over one huge partition | `winstream.go:89` | needs the rows in the child's order, and max and average a peer group's end |
| a reversed cum_sum, cum_prod, cum_min or cum_max | `winstream.go:66` | a row's answer depends on every row after it |
| an unlimited backward fill | `winstream.go:78` | the same |
| interpolation | `winstream.go:89` | a row needs the next valid value, however far |
| rolling by time over one huge partition | `winstream.go:80` | a window's rows are bounded by time, not count |
| a window with no partition_by beside a keyed one | `extwindow.go:61-71` | `streamable` needs every partitioning keyless |
| a growing aggregate in `.Over()` (median, quantile, n_unique) | `winstream.go:160-169` | the one-partition path never spills values |
| n_unique over a hot key, or with no key | `extagg.go:272-289` | its state is O(distinct values), and it does not spill |
| keyed `Rolling` and `GroupByDynamic` | `tempsegment.go:42-47`, `tempstream.go:491-509` | every window's state is held: the answer comes out bucket by bucket, and the last row may still add a window to the first bucket |
| join_asof's read-ahead | `asofstream.go:462, 565` | a left by-key the right side lacks reads that side to its end |
| top-k with a large k | `sort.go:128` | `compact` neither spills nor checks |
| a dynamic group's long index gap | `tempstream.go:198-224` | every empty window is made before any is handed out |

**What stays refused:**

- **a single join key with more build rows than the limit,** and a group too large

## 2. Windows: one sorted pass for each distinct order

The one-partition file F (`startOneSpill`, `winstream.go:110`), at level 0 or for a
hot key, is written as now. For each group of specs sharing an order:

1. **Project.** Read F, stamping a local dense `__pos` the same on every read, and
   project a narrow batch:
   - `__pos`;
   - the order keys as `__k{i}`;
   - each spec's child and fill as `__c{i}` and `__f{i}`.
2. **Sort forward** with a `sortSink` built by hand, keys `[order keys…, __pos]`.
   `__pos` makes the order total, so it equals the in-memory stable sort and does
   not depend on the order runs merge in.
3. **Walk** with `winStreamOp`'s logic, generalised to any run source. The specs are
   rewritten to read `__c`/`__f` with no order.
4. **Walk backward,** for the steps that need it: a `reverseSink` over the forward
   stream, exactly its reverse, so peers, nulls and ±0 agree with the kernels'
   reverse walk.
5. **Sort back** by `__pos` into an answer file.
6. **Zip.** The final walker reads F, as today, and splices in each answer file's
   columns.

The output is the window's schema in F's order, so the hot-key merge on the ordinal
(`winskew.go:115`) is unchanged.

**Per function:**

- **ordered bounded functions** (shift, forward cumulatives, cum_count, ewm, the
  fills, rolling by rows, under an order_by): the forward walk alone;
- **reversed cumulatives and the unlimited backward fill:** the backward walk, with
  `Reverse` cleared and `bfill(0)` as `ffill(0)`;
- **rank:** `kernel.RankNext` carries a position, a dense count, a group's first rank
  and the last value:
  - ordinal, dense and min are answered forward;
  - max is `n + 1 − minRev`, minRev being min rank on the backward walk;
  - average is `(first + last) / 2`, computed as the kernel computes it;
- **interpolation:** forward carries the previous valid value and its position,
  backward the next; each row is answered from both, as the kernel's formulas do.

**Order keys** of struct or list type are refused alike in memory and on disk,
before any input is read: the merge's key types are those the in-memory comparator
takes.

**Memory:**

- the sorts and the reverse spill when they themselves hold a quarter of the limit,
  as well as when the query is over it;
- the sort merges 16 runs a level, as the value spill does;
- the walker is accounted.

**Rolling by time** is Tier 2: the same pass, keyed by the `by` ticks, with a
time-bounded window whose memory is set by the densest period.

## 3. Holistic state

- **n_unique spills its values.** The step-220 value spill is generalised to (group,
  key bytes) runs, sorted by both. Finish counts the distinct adjacent keys of each
  group as the runs merge. The group-key encoder's bytes make NaN equal NaN and −0
  equal +0, so equal bytes are equal values.
- **A growing window aggregate spills** through the same spills, in the
  one-partition path, before it refuses.

## 4. Keyed Rolling and GroupByDynamic hand their answer out

1. **Close by a watermark.** The index is sorted across the whole input, so a window
   whose end the last row has passed is final, in whichever bucket.
2. **Segment.** Windows are handed out in segments for keyed groups too, each row
   carrying its key, a hidden bucket number and a window number.
3. **Restore the order.** An external sort on (bucket, window) restores today's
   bucket-major order before the projection drops the hidden columns.
4. **Spill values.** A rolling median's windows spill their values as group-by's do.

## 5. Tier 2

- rolling by time over one huge partition;
- join_asof's read-ahead spilled as tail's runs are;
- top-k with a large k sorted externally;
- a dynamic group's empty windows made as they are handed out.

## 6. Claims

For each item:

- it answers under a budget a tenth of its input, where it refused;
- its answer is frame-equal to the in-memory one, on one thread and four;
- the spill directory is empty after success, after an error and after an early
  break;
- the tests that asserted its refusal flip.

The windows' sorted pass also peaks at about twice the budget or less.
