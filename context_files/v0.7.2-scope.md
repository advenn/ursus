# ursus v0.7.2 — scope

**Theme: finding the bugs, and fixing them.** Nothing else.

The maintainer set it on 2026-10-31, once 0.7.1 was out: "version: 0.7.2, dedicated
to bug hunting and fixing". They had stopped the move to 0.8 the day before ("why
rushing to 0.8?"): nobody but its author has checked the code, so nobody can stand
behind it in production, and the bugs found lately suggest more elsewhere.

0.7.2 is a patch on the 0.7 line. It is built on `release-0.7`, v0.7.1's code, by a
branch and a pull request for each piece of work, with nothing pushed to a release
or to master directly. A fix reaches master too, by a pull request of its own, so
that 0.8 carries it. 0.8's own code, the shared engine, the hook, `ursus.Error`, the
fs.FS readers and step 400's rewrites, is not on this line; it gets the same hunt,
with the tools built here, before 0.8 is released.

**Where it stands:**

- written at step 410.

## 1. What the survey found

Step 410 surveyed the project from master's tree at step 409. It read every as-built
record, the CHANGELOG and the feature-gaps, and the code; and it measured coverage
over the whole suite. Three agents did the reading, and one finding was checked by
running it.

### How it was built

- **Fast, by one author:** 56 days, 634 commits, about 120,000 lines of Go and
  112,000 of tests.
- **A fix for nearly every feature:** 143 commits are fixes against 171 features, and
  the rate rises: 52 in September, 91 in October.
- **No user yet:** no issue has ever been filed.

### What the tests check against

- **The code runs under test:** across packages, the suite runs 89.9% of all
  statements, and 4,767 never. The functions no test enters are mostly a node's
  `Schema` or `Name`.
- **The answers they expect are the author's own:**
  - about 109 test files say "every answer is Polars 1.44.1's", but their answers
    are Go literals typed by hand that nothing checks against Polars;
  - 14 files are worked by hand;
  - the 34 golden plans are recorded from the code's own output;
  - only 101 expression cases, `testdata/oracle/expressions.json`, were recorded from
    Polars by a script, and a few fixture files from Polars and pyarrow;
  - DuckDB checks the 22 PDS-H queries, and h2o's 15 by their row counts and column
    sums.
- **Nothing random checks against another engine:** no test pairs random data or a
  random query with DuckDB or Polars. 96 test files draw random data, from fixed
  seeds, and check it against the code itself.
- **Self-consistency tests exist but are small:**
  - the optimizer on and off, about two dozen transforms on an 8-row fixture;
  - pruning on and off;
  - batch sizes and threads, about 20 sweeps;
  - spilled against in memory, at 1,200 rows.
- **Fuzzing barely exists:** two targets, `FuzzEvery` (the interval parser) and
  `FuzzHybrid` (Parquet's run-length decoder). CI runs only their seeds. No reader
  is fuzzed.

### What found the bugs so far

- **An audit against outside engines** found 78 defects at once, about 40 of them
  silent wrong answers (step 69, `audit.md`). Reviews of earlier work found 22 more
  (steps 118–122).
- **A feature's own tests and teeth** found about 60 to 80 on the way, each in the
  feature being built.
- **The benchmarks against DuckDB** found about 6; CI's race detector 4; a byte-flip
  sweep of Parquet files, once, 118 panics and a hang (step 72).
- **Bugs between features stayed for long:**
  - `FillNull(FillForward)` filled every null with 2 from the first commit to step
    249;
  - a cancelled query returned part of its input as the whole from step 5 to 394;
  - a null ranked smallest from step 8 to 335;
  - `RollingOptions.Offset` differed from Polars' from step 14 to 313.
- **Mutation tests, the teeth:** about 2,650 recorded, about 135 of them silent; most
  of the silent ones are equivalent or speed-only, and about 20 are real gaps, listed
  in step 410's record.

### Open now

**Confirmed:**

- **A crash, which no recovery catches:** a line of deeply nested NDJSON overflows
  the goroutine's stack, `fatal error: stack overflow`, and the process ends.
  `ndjson/value.go` recurses once a level with no limit, and `kernel/strjson.go`'s
  `readJSON` likewise. Run at step 410 with the stack capped at 64 MB: 2,000,000
  levels, a 4 MB line, end the process. At Go's default 1 GB, a line about sixteen
  times deeper does the same.
- **Wrong answers in the last bits:** a float `Sum`, `Mean`, `Var`, `Std`, `Skew`,
  `Kurtosis` and `Entropy` differ between one thread and eight (step 287); a
  streamed rolling var, std, skew, kurtosis, cov and corr under a memory limit differ
  from the answer in memory in 35 to 52% of rows (steps 284, 287).
- **A naive Datetime printed and cast to String with a "Z",** as if it were UTC
  (step 296; `dtype/temporal.go`). The CSV writer was fixed at step 354.
- **A corrupt Parquet file read without an error:** in step 72's byte-flip sweep, 510
  of 1,146 reads, page checksums being neither written nor checked; arrow-go
  swallows a page's decode error, which then reads as missing rows (step 83).
- **Refusals that mislead:** a join under a small limit blames "a single join key"
  for memory another operator holds (`extjoin.go`, steps 307, 314);
  `WithColumns(IntRange(0, Len(), 1))` beside a string column is refused under a
  limit (step 287).
- **A flaky test:** `TestTemporalMediansSpillTheirValues`' heap bound, under load
  (steps 292, 304, 339, 344).

**Suspected by reading, each to be probed before it is called a bug:**

- a Parquet dictionary page allocates by its header's count before checking the page
  is that long (`parquet/pages.go`, `dictfilter.go`): a small page could ask for
  gigabytes;
- an Arrow IPC ListView whose rows share one child range reserves up to 2³¹
  elements (`arrowin/builder.go`);
- a cached plan node's result may hand every reader the first caller's cancellation
  (`physical/cache.go`, `once.Do(drain(ctx))`);
- a Struct, Enum or time zone type, once built, is kept for the process's life
  (`dtype/intern.go`): a service reading varied data grows without bound;
- `hive.Escape` leaves `\` as it is, so a partition value of `..\..\x` may write
  outside the target on Windows (`hive/hive.go`);
- the memory ledger keys a buffer by its address, so a slice held beside its parent
  may count twice (`execopt/budget.go`);
- Min and Max of -0 and +0 answer whichever came first, which a test comparing -0 ==
  0 cannot see;
- a business day's `Add` computes `d + 7*w` with no overflow check
  (`kernel/dtreplace.go`).

### Where the next bugs most likely are

Ranked by the survey:

1. **The spill paths:** the spilled join's three split states, the null-key bucket,
   the semi and anti rules, the depth limit; `winstream.go`'s six kinds of carried
   state. They run only under memory pressure, and a sweep covers each at 1,200 rows.
2. **0.7's own rewrites,** covered only by their own tests:
   - integer keys packed into words (`kernel/wordkeys.go`, `physical/groupkeys.go`);
   - Parquet's columns read at a text filter's kept rows (`parquet/dictfilter.go`);
   - pooled page buffers (`parquet/pool.go`);
   - filters pushed below a group-by or a window (`rule_predicate.go`);
   - windows over a group's list, and the large top-k.
3. **The readers on untrusted input:** none is fuzzed; see the crash and the
   suspected allocations.
4. **Type resolution and casts:** `expr/call.go`, 16 fixes; `kernel/unary.go`, 18;
   Parquet's types and columns, 12 and 11.
5. **Concurrency:** an aggregate a parallel group-by merges in any order unless
   `IsOrderDependent` names it, by hand; the process-wide memory limit the first
   query sets.
6. **Windows, rolling and dynamic groups:** many order, offset and closure variants,
   several fixed to Polars' after the fact.
7. **The optimizer:** `substitutable` rebuilding a call as if every call were
   row-wise; `rule_projection.go`'s 389-line `pushdown`.
8. **Time zones:** `kernel/tzreplace.go`'s gap and overlap resolution; `strftime`'s
   greedy number parsing.
9. **`unsafe`:** `fromrows.go`'s walk of a caller's structs by field offsets, under
   one test function.

## 2. The rules of 0.7.2

- **Fixes only.** No feature and no speed-up. A change of public API waits for 0.8:
  0.7.2 may add no break, and is checked so (H0).
- **A bug is what data does.** A file, a frame or a value a caller reads must give
  an answer or an error: never a panic, a hang, a fatal error or an allocation far
  past its size. A programmer's out-of-range index may panic as Go's own indexing
  does, documented.
- **Every bug found becomes a test,** minimized, that fails before its fix.
- **An answer is checked against another engine where one exists,** not against the
  author's expectation. Where ursus differs from Polars on purpose,
  `feature-gaps.md` §9 says so, and the harness reads the same list.
- **Each piece is a branch and a pull request into `release-0.7`,** CI green before
  it merges; the maintainer merges. Each fix then goes to master by a pull request
  of its own.

## 3. The work

### H0. The workflow

- the documentation built on a pull request, without publishing it;
- a pull request's checklist: the test that failed first, an outside answer where
  one exists, the teeth, the gate;
- the API check on this line: master's `internal/gen/api` with `-dir`, against
  `api/v0.7.1.txt`, so no feature of v0.7.1's goes;
- master and `release-0.7` protected so that a change comes by a pull request with
  CI green, on the maintainer's word.

### H1. The crash

NDJSON's and `JsonDecode`'s nesting gets a depth limit, beyond which the read is an
error naming the line; the other recursive readers are checked for the same, the
JSON reader's and the Arrow importer's nested types among them.

### H2. The suspected, probed

Each item of §1's suspected list gets a probe, a test that shows it or shows it
cannot happen; what is real is fixed. Corrupt Parquet is decided here: page checksums
written and checked, or the reader's own checks where arrow-go's are silent.

### H3. The known, fixed or decided

- the naive Datetime's "Z";
- the float aggregates that move with the threads: an order of combination that does
  not depend on them, measured for its cost first, or recorded as a difference;
- the streamed rolling moments, made to equal the answer in memory;
- the misleading join refusal and the spurious `IntRange` refusal;
- the flaky heap bound;
- the real gaps among the silent teeth.

### H4. Fuzzing

- **Go fuzz targets** for each reader, CSV, NDJSON, JSON, Parquet, Arrow IPC's file and
  stream, from bytes; for `strptime` and `strftime`; the float parsers and the casts
  from text; `i128` against `math/big`; each SIMD kernel against its scalar twin, at
  random lengths and offsets.
- **A sweep of real files,** each truncated at every length and flipped at every byte,
  in CI.
- **The outcome a target checks:** an answer or an error, in bounded time and memory.

### H5. Random queries against DuckDB

- **A generator of tables:** nulls, NaN, ±0, the extremes of each type, empty
  tables, Unicode and long strings, dates and instants across zones.
- **A generator of queries over the lazy API:** filters, projections, casts,
  arithmetic, group-by aggregates, joins of each kind, sorts, uniques, windows, and
  the string and temporal functions.
- **Each query in SQL for DuckDB,** run in the same process through `duckdb-go`, as
  `bench/engines/go/duckdbengine` does, in a module of its own so that ursus's
  `go.mod` gains nothing.
- **The answers compared:** row order where the query fixes it; floats to a stated
  tolerance; §9's differences as rules.
- **A mismatch shrunk** to the smallest table and query that show it, and kept as a
  test.

### H6. The same queries against themselves

Each random query of H5 must give one answer:

- on 1, 4 and 8 threads, and in batches of 1 to 64 Ki rows;
- under a memory limit that makes it spill, and without one;
- with the optimizer off;
- read from memory and back from Parquet, CSV and IPC.

No oracle is needed; it aims at §1's ranks 1, 2 and 5.

### H7. The typed answers, checked against Polars

A script runs the cases of the files that say their answers are Polars' in Polars
1.44.1 and compares them with the Go literals; a case it cannot run is listed. The
oracle file grows by what it can run.

### H8. Many queries at once

A soak:

- many queries on one process, with random cancellations and deadlines, a cached
  plan shared among them;
- under the race detector, with no goroutine left, no spill file left and no memory
  held after.

### H9. A review of the riskiest code

§1's ranks 1 to 4 and 7 to 9, each read by a reviewer with no part in writing it, a
fresh agent, and each finding checked by another before it counts; what holds becomes
a test. It is still a machine checking a machine: a person reading the spill paths,
the optimizer and the readers is the only independent check, and whether one does is
the maintainer's choice.

## 4. Where the long runs go

Not on the laptop, which has the maintainer's work on it and no memory to spare. A
pull request runs each fuzz target and the random queries for a short while, in CI;
a nightly scheduled run, on GitHub Actions, runs them for hours, if the maintainer
agrees. A finding is kept as its seed and its minimized test.

## 5. When 0.7.2 is done

- H1 to H3's lists are empty, each item fixed or decided and written down;
- a week of nightly runs of H4 to H6 with no unexplained finding;
- H7's mismatches fixed or recorded; H8's soak clean; H9's findings tested;
- no flaky test;
- the 22 PDS-H answers match DuckDB's, and the suites are no slower than v0.7.1's,
  alternated;
- the CHANGELOG's 0.7.2 section lists each fix. Then the tag, on the maintainer's
  word.

## 6. Order

1. step 410, this scope;
2. H0, then H1, the crash;
3. H2 and H3, a pull request each item or a few together;
4. H4, fuzzing, which finds crashes cheaply;
5. H5 and H6, the random queries, the largest piece;
6. H7 and H8;
7. H9, alongside, as each area is reached;
8. the report and the tag.
